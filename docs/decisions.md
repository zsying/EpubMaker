# 设计取舍

记录"为什么是这样"，避免以后有人（包括我自己）把已经否决过的方案再提一遍。
每条都给出当时的证据，而不是偏好。

## ADR-1 无 HTTP、无端口

原来是 Express 后端 + `/api` 路由，迁移到 Wails 后留了一层薄 HTTP。后来全部删掉：
前端只调 `api.ts` 封装的进程内绑定（v2 时代是 `window.go.app.Backend.*`，v3 起是宿主自己的
`/wails/runtime.js` + `Call.ByName`），二进制响应内联 base64。

原因：桌面单机应用里，HTTP 层只带来三个问题——端口冲突、dev 与生产两份路径、CORS/代理配置。
进程内绑定让 dev 和生产走同一条路径，打包成单 exe 也不再有资源服务器。
代价是大文件要走 base64（约 +33% 内存峰值），在单本 EPUB 的尺度上可以接受。

推论：**任何需要"再起一个服务"的功能都别想**，包括内置词库的 HTTP 查询、LLM 代理。

## ADR-2 资源主键 = 原 zip 内完整路径

落盘 `books/<id>/content/<原路径>`，导出原样还原。曾考虑扁平化（`images/0001.png`）以便管理，
但章节里的相对引用（`../images/x.png`）会全部失效，导出时还得反查映射。
保留原路径后，相对引用天然成立，导出逻辑几乎不需要资源重写。

代价：路径可能带 `..`、重名文件、大小写差异，必须在 `storage.ContentPath()` 里统一做穿越防护。

## ADR-3 翻页动画：只动像素，不动排版

（原标题是「分页翻页不做动画」，2026-10-27 重做了一次。两次的取舍都留在这里。）

第一次：8 个 commit 的 3D 翻页（`.flip-turner` 双面各塞一份完整章节 HTML + `mix-blend-mode` 高光），
在 WebView2 上严重卡顿，也没有实体书手感，已整体删除。当时留下的规则仍然有效，这次就是照它做的：
**一次翻页只允许一个活动图层，不要复制整章 HTML。**

现在的做法：章内翻页 = 列条按一页（或一个跨页）宽做 210ms 的 `translate3d` 过渡，
外加一层纸影朝同一方向扫过（`.turn-veil`，宽 34%、峰值约 14% 黑；深色主题加深到 ~48%，
否则近黑纸面上的阴影根本读不出来）。列条本来就已经是独立合成层（手机上实测
15,534×2,142 设备像素），所以这是 GPU 动画，主线程卡一下也不影响它继续走
——录屏实测一次翻页 21 帧、19 帧画面各不相同、间隔中位数 20ms，是连续位移而不是几段跳。

**触摸手势翻页由手指驱动，不是由定时器驱动**（2026-10-27 第二版）。手指按下并横向移动后，
页面 1:1 跟着走（`.reader-drag` 这层只承载拖拽偏移，无过渡）；松手才决定结局：走了 1/3 页
（或快速甩动 > 0.5px/ms 且超过 16px）就滑完这一页，否则滑回原处。两种结局都是同一个
210ms 滑动，所以「翻到一半再放下」是页面真实经过的状态，而不是事后补一个动画。
细节：

- 键盘 / 滚轮 / 点页边仍走固定 210ms 过渡（没有手指，没有要对齐的东西），两条路径
  的时长和曲线一致，视觉上是同一个动作。
- 拖拽偏移写在**单独一层** `.reader-drag`（`.reader-clip` 与 `.reader-columns` 之间）：
  列条自己的 transform 会被 measure / restore / 1↔2 分栏重写，拖拽偏移混进去就得每次
  重新贴回去。这层常开 `will-change: transform`，否则每帧重新栅格化整章（15,534px 宽）。
- **提交页码放在滑动结束的那一刻**，不是在松手时：松手时只把拖拽值滑到 ±1 页，`transitionend`
  才 `setPageIndex` 并丢掉偏移（在同一个 commit 的 layout effect 里，不会出现夹帧）。
  这样「从手指当前位置滑到终点」和「页码跳变」是同一件事。
- **新触摸可以接管正在回落的页面**（连续快速翻页必需）：`getComputedStyle` 取当前值把页面
  钉住，再以它为原点继续跟手。注意 Chrome 里**运行中的过渡不会被「删掉声明它的 class」中止**，
  也不会被新的值顶掉——它会一路走到旧目标。要停在原地只能 `transition: none` + 强制一次
  style 重算（这次重算不会被绘制，所以看不到跳变），然后写新值。
- **章节边界也跟手，前提是「真的有一页可拉」。** 列条只装本章，硬拉就是拉到空白纸上——
  第一版因此在边界处退回淡入淡出。现在边界处会先把相邻章节的那一页**按与当前页完全相同的
  几何预排好**（`TurnPeek`：同一 `margin / contentWidth / contentHeight / columnGap`，
  宽度按列数算、末页用同一个 `lastTextPage` 定），停在屏幕外**一个跨页宽**处
  （`translate3d(±stride)`；静止位只由 layout effect 写一次，拖拽期间每帧直接写 DOM，
  React 不覆盖它）。于是离场页和到来页被同一个偏移带走，是一条连续的页面对。
- **peek 只在「还能再翻一页」的那一页预取**（`pageIndex + pagesPerView >= pageCount` 或首页），
  延时 160ms 拉一次 `RenderChapter`，`DOMPurify` 后进 `peekCache`（上限 3 条）。
  拖拽进行中不拆 peek（effect 直接 return），否则手指刚落下、被拉的那页就消失了。
- **换章用交接，不用再闪一下**：滑过阈值后不立刻换页，先 `openChapter(target, {first|last})`，
  新章节在 peek 挡着纸面的情况下完成加载与测量，`measureAndLayout` 里一个
  `requestAnimationFrame` 同时丢掉拖拽偏移、清 drag、清 peek——三者同帧切换，所以看不见。
  反方向拖能把控制权交还给列条（`kind: 'chapter' → 'page'`，peek 滑回原位），
  所以「拉出来又推回去」不会被吞掉。
- **末页不能数盒子**：`Math.ceil(scrollWidth / stride)` 数的是列盒，末段落多出几像素就多一个
  空列，而回翻正好落到那一页（读者要空翻一页、页码还停在 11/12）。现在 `stripCols`（盒子占几列）
  与 `pageCount`（有文字的页数）分开，后者由 `lastTextPage()` 量最后一个非空白字符所在列；
  同理 `offsetForPage` 在末页会返回「全图最后偏移」（映射回去是前一页），测量改走
  `pageStartOffset()`——它诚实地对「映射里没有这一页」返回 `null`。
- 真机（JEF-AN00 / Android 12 / WebView）实测跨章：手指拖 60 / 140 / 240px → 页面
  60 / 140 / 240px、peek 同步 -314 / -234 / -134，松手落在上一章末页并有字，
  空闲 600ms 共 38 帧、0 帧 >34ms（peek 是一整章在排版，掉帧风险最高的就是这里）。
- `prefers-reduced-motion: reduce` 下完全不跟手，滑动也不画影子、不铺 peek，翻页瞬时完成。

三条硬约束，破坏任何一条，「不干扰阅读」就变成「页面在抖」：

1. **过渡挂在 `.reader-spread.turning` / `.turn-settle` 上，不挂在 `.reader-columns` 上。**
   同一个 transform 会被 measure / restore / 1↔2 分栏反复重设，常驻过渡会让文字从第 1 页飞过来。
   验证方式不是看截图，而是逐帧断言 clip / spread / 页数 / 页码在翻页期间一动不动。
2. **收尾用纸影的 `animationend`（手势路径用拖拽层的 `transitionend`），不用固定延时。**
   运行中的过渡不会被删掉的声明中止，它会继续跑到旧目标值——所以用 setTimeout 收尾，
   主线程一卡就变成「滑一半、啪一下跳过去」，而且 class 没了、页还在动。
   `prefers-reduced-motion: reduce` 下纸影是 `display:none`，永远等不到事件，所以另留兜底超时。
3. **页码属于页张槽位，不属于列条**：翻页一开始就 90ms 淡出，结束再淡入，否则它会抢在
   文字前面跳到新的角上（被手指拖住时也一样，页码跟着页面离开）。

章节切换现在也是滑动（见上）；只有**没有相邻页可拉**的时候才退回 130ms 淡入淡出
（单章书、或相邻章节拉取失败）——那是在盖住新章节 HTML 异步加载的空窗，不是装饰。
`TurnPeek` 预取失败不影响正确性，只是这一次退化成淡入淡出。

## ADR-4 词库不联网下载，走本地导入

实测官方 `raw.githubusercontent.com` 下载 `ecdict.csv` 约 **1.4 KB/s**（6 分 48 秒只拿到 557KB），
100MB 要十几小时。所以"首次运行自动下载词库"这个方案直接排除，不再讨论。

现状：随包分发或用户自备 csv，走 `DictImportCSV`（界面按钮 / `cmd/dictimport` 同一代码路径）。
全量 770,611 条导入耗时 8.5 秒，所以不需要进度条，按钮禁用 + 菊花即可。

词库独立放在 `dict/dict.db`（不塞进主库），是为了能整体替换、重建、删掉而不影响书库。

## ADR-5 生词本是跨书资产

`vocab.book_id/chapter_id` 只存值，**不加外键、不级联删除**。
同一个词在 A 书、B 书都会遇到；书删掉、读完了，词还得留在复习队列里。
如果挂在 `book_id` 上做级联，整理书库会顺手毁掉学习积累——这是不可接受的耦合。

## ADR-6 变形词不覆盖原型

原以为"`running` 应该还原成 `run` 再查"。完整词库证明这是错的：

- ECDICT 把每个变形都收成了独立词条，所以还原逻辑根本不触发；
- 但变形词条的释义往往只是"v. 爬（climb 的过去式和过去分词）"，只给这个等于没解释；
- 而 `running` 又有独立实义（赛跑、流动的、运转的），替换成 `run` 会丢信息。

结论：`Result.Base` 同时返回原型，界面并排显示"本体释义"+"原型及其释义"。

## ADR-7 自动入库：高频不收录 + 第二次才收录

系统没法知道哪些词"你不认识"，能捕捉的只有"你查过它"。所以自动记录 = 查完零点击入库，而非智能识别。

两个过滤条件，目的是让生词本第一页就可读：

1. **高频词永不自动收录**（`frq`/`bnc` ≤ 5000）。否则 `the`/`of`/`a` 会瞬间淹掉列表。
2. **同一个词第二次查才入库**（`vocab_seen.lookups ≥ 2`）。隐式表达"我真的不认识"，而不是"我好奇一下"。

手动"加入生词本"永远可用，不受上述限制；标过 `known` 的词不会因为再查一次被降级。

已知让步：因为词在第二次才入库，**例句只能是触发入库的那次出现**，第一次的句子没被存过。
要保住"第一次的句子"得给信号表加 4 列存首次出处，为一个例句微调不值得，已写进代码注释与测试。

## ADR-8 复习用 SM-2 排程，而不是"每天全过一遍"

上一版复习是"把没掌握的词按顺序过一遍"：没有间隔，没有下次时间，同一个词可能今天答对、
明天又出现在队首。那不是间隔重复，只是把列表换了个顺序。

现在按 SM-2（Wozniak, 1987）排程，落到五个字段：

| 字段 | 作用 |
| --- | --- |
| `interval_days` | 当前间隔（天）。0 = 从未排程（立即到期），< 1 = 十分钟重学步 |
| `ease` | SM-2 熟练度系数，起始 2.5，答对 +0.1、答错 −0.32，夹在 [1.3, 2.8] |
| `due_at` | 下次到期时间，RFC3339 UTC 秒精度；空串 = 从未排程 |
| `streak` | 连续答对次数（展示用，算法看间隔本身） |
| `lapses` | 累计答错次数 |

打分的两条路径：

- **认识**：`interval ≤ 0 → 1 天`；`< 1 → 1 天`（从重学步毕业，先挣一天）；`< 6 → 6 天`；
  其余 `round(interval × ease)`。间隔到 21 天才算 `known`——**掌握是证据，不是一次点击**。
- **不记得**：回到 10 分钟重学步，ease 下调，`lapses+1`，状态 `learning`。

为什么是 10 分钟而不是 1 天：答错时记忆最薄弱，当天再见一次才有用；推到明天等于放过。

为什么用两档而不是 SM-2 的 0–5 六档：卡片只有两个按钮。把六档硬塞进界面的结果是
用户永远只点中间那个，数据反而更差。两档 + ease 已经足够把"总也记不住的词"和
"一眼就过的词"区分开——前者间隔涨不上去，后者越排越远。

`due_at` 用定长秒精度字符串而不是 SQLite 的 `datetime()`：一是 **字符串比较即时间顺序**
（RFC3339Nano 不满足，`…:00.5Z` 会排在 `…:00Z` 前面），二是 Go 侧算好再比较，
不依赖 SQLite 对纳秒小数的解析行为。

队列因此只剩一句判断：`status <> 'ignored' AND (due_at = '' OR due_at <= now)`。
`known` 不再等于"永不出现"——间隔到期的老词会回来，这才是长间隔复习的意义。
手动点"已掌握"不记为复习，但会把下次检查排到三周后（`ignored` 才是真正的退出）。

已验证：1 → 6 → 16 → 45 天的阶梯、答错回到 10 分钟步、ease 触底 1.3、
到期的 `known` 词会重回队列、老库迁移后旧词一律"立即到期"（各有测试）。

## ADR-9 拖放导入走 Wails 原生桥，而不是 HTML5 拖放

书架一直写着"拖入 epub"，但实现是 `onDrop` 里 `preventDefault()` 之后调用
`SelectEpubFiles` —— 也就是拖完弹一个文件选择框，等于没导入。原因不是懒：webview 的
drop 事件里只有 `File` 对象，**没有文件系统路径**，而这个应用的导入是"从磁盘读"，
从来没有上传通道（见红线 2）。所以在纯前端里那份拖进来的数据是读不出来的。

现在的路径：`main.go` 打开 `DragAndDrop.EnableFileDrop`，Wails 把 drop 坐标与
WebView2 的 additional objects 交给 Go 侧解析成绝对路径，再以 `wails:file-drop`
事件回传前端；`web/src/filedrop.ts` 订阅一次，把路径交给书架页已有的
`ImportPaths`。前后两个入口（按钮、拖放）在 `Library.importPaths()` 汇合。

三个必须同时成立的点，缺一个就退化：

1. `EnableFileDrop` 为真 —— 否则 Go 侧直接丢弃 `file:drop` 消息；
2. 前端订阅了 `OnFileDrop` —— Wails 的 window 级 `dragover/drop` 监听是**随订阅安装**的，
   没订阅时连 `preventDefault` 都没有，拖进来的文件会把 webview 导航过去（页面变成一本
   epub 的二进制），这是本 bug 之外更严重的默认行为；
3. `useDropTarget: false` —— 默认值要求落点元素带 `--wails-drop-target` CSS 属性，
   而书架希望"拖到哪都能放"，所以关掉它，由页面自己判断该不该导入。

订阅放在 `App` 而不是书架页：它同时是"拦住默认导航"的那一层，晚一步注册就有一个
drop 仍然会毁掉页面。

拖到书架以外的页面不导入，只提示回书架 —— 导入要落到书架的列表状态上，别的页面没有
可更新的东西，静默失败比一句提示更糟。

降级：浏览器里没有 `window.runtime`（`run.ps1 web` / 纯前端调试），`canResolveDropPaths()`
为假，drop 退回打开文件选择框 —— 那条路仍然有路径，仍然能导入。

## ADR-10 0.4 AI 能力：BYOK + 底部面板 + 全链路 grounding

原型：`docs/prototypes/0.4-ai-mobile.html`（2026-10-25 与用户逐屏定稿）。

范围（按优先级）：

| 能力 | 触发 | 喂给模型的本地数据 | 优先级 |
| --- | --- | --- | --- |
| 上下文释义 | 词卡「✦ AI」 | 原句（`LookupWord` 第 7 参早已传入并落库）；**义项不发了，见文末修正 1** | P0 |
| 整句翻译 + 长难句拆解 | 划词工具栏「✦ AI」 | 选区句子（`sentenceAt` 已取到） | P1 |
| 章节导读 | 顶部工具条「✦ AI 导读」 | 章节正文（截断 6000 字，发送前明示） | P1 |
| 人物卡片 | 读完一章 | 各章导读结果合并去重 | P2（可选） |

**原句填空出题押后（v0.5 候选）**：初版设计是 mask 生词本已存的 context 句让用户填。
否决理由（用户提出）：例句本就印在复习卡上，遮一个字再填回去只是重复回忆同一句话，
边际价值接近零，还会诱导「照着句子找词」而非回忆词义。重启方向：先跨章检索该词在本书
其他位置的真实出现（零生成、真实语料），不够再让 AI 按书中风格造新例句。

### 为什么是 BYOK，不做内置代理

内置代理 = 给「无服务端」应用加服务端（ADR-1 的推论明确点名了 LLM 代理），
还引出计费与密钥中转的隐私问题。所以：设置页填 base URL + key + model
（预设 DeepSeek / 通义 / Kimi 等 OpenAI 兼容端点），密钥存本机 0600 文件。
**没有 key 时全部功能照常**，AI 入口显示「未配置」并引导去设置——AI 是可选层，
不是门槛。

### 入口形态：底部面板（方案 C），不是词卡内嵌（方案 A）

| 维度 | A 词卡内嵌（未选） | C 底部面板（选定） |
| --- | --- | --- |
| 操作步数 | 1 次点击 | 2 次（点按钮 + 看面板，可滑动关闭） |
| 词卡负担 | 结果让词卡变长 | 保持轻量，和现在一样高 |
| 长内容适配 | 义项高亮、结构化拆解排不开 | 面板 76% 高，结构化展示 |
| 手势风险 | 无新增 | 模态需排除 swipe 翻页（红线 5f，抽屉已有先例） |
| 实现成本 | 只改 dict-card | 新增面板组件（三个 surface 复用） |

「一步看完」让位于「长内容展得开」：拆解输出是结构化的，卡内一行行排会挤；
且面板组件三个 surface 都要用，单点成本摊薄。

### 翻译与拆句合并为一个视图

不拆 tab：手机上 tab 是隐藏内容，用户永远只看到第一个；译文 + 拆解一次请求、
一个滚动视图看完，信息密度更高。缓存键 = 精确提示词的 hash（实现期修正：
原设计是「句子文本」，改为 system+user 整段 hash——提示词改进会自动失效旧缓存，
用户为更好的答案再付一次费，是正确的行为）。

### 隐私确认：每次问

导读是唯一发送整章正文的功能，不提供「记住选择」——每次发送前都明示
（字数 + 服务商），这是红线 2a「显式动作」在正文尺度上的执行方式。
其余能力只发单词/句子，不需要额外确认。

**实现期修正（0.4 收尾）：确认框先做配置预检。** 没有配置时弹「还没有配置」
+ 去设置，而不是让用户点完「生成导读」再收到一个错误——一个只能以失败告终的
确认框不算确认。同时 `NotConfigured` 的错误文案带上 `ai.json` 的实际路径：
「我明明配了」几乎总是另一个 `AppHome` 下的第二份配置，路径一眼就能定位到问题。

### 导读入口：顶部菜单，不是章首浮标

设计期放在章首浮标（`position: fixed`，只在第 1 页/滚动到顶时可见），理由是
不能往正文流注入（红线 6）。实机使用后 john 判定入口位置错了：浮标压在第一行
文字上方，读起来像正文的一部分，而且只在章首存在——想再看一次得先翻回章首。

改为顶部工具条里的一个按钮（手机是返回/标题/✦AI/书签那一排，桌面是与
目录、书签、滚动同排的 `✦ AI 导读`）。章首浮标与它的滚动跟踪一起删除，
正文上方不再有任何浮层。代价是手机上要先点一下上下边距打开工具条，
收益是它和「目录/书签」同类归位，任何一页都能用。

### 红线对照

- 2a 显式触发：全部能力都是点击触发，无任何打开页面即请求；
- 2 无 HTTP：前端只调 `Backend.AI*` 绑定，二进制内联 base64 的老规矩不变；
- 2b 超时：单次 15s 上限，失败 UI 给重试、**不写墓碑**——与 `FillVocabGlosses`
  的区别：那是不存在的词（写墓碑避免重问），这是网络故障（下次还该能重来）；
- 2c 落缓存：新表 `ai_cache`，key = 精确提示词 hash；**只有非空回答落缓存**
  （实现期修正：空回答也不写墓碑——空回答是软失败，「重试」按钮必须永远真实，
  空回答走缓存会让用户以为已经问过了）。网络/HTTP 故障同样不写。
  二次查看零延迟、离线可回看。

### 实现顺序

`internal/ai`（OpenAI 兼容客户端 + ai_cache 存取）→ Backend 绑定 → 设置页 →
阅读器三处入口。先写测试（httptest 假服务商）：缓存命中、墓碑/重试语义、
超时、错误映射、上下文裁剪。

### 验收后的四处修正（2026-10-26，真机 + 用户反馈）

**1. 上下文释义不再喂义项，改成「直接解释 + 整句翻译」。**
原设计（本 ADR 首版）是让模型在 ECDICT 的编号义项里挑选，理由听起来更「grounding」。
实机第一次用就露馅：ECDICT 把一个词的全部义项塞在一行里
（`n. 1.儿童，小孩 2.婴儿，胎儿 3.子女，孩子 …`），模型拿到这种「大杂烩义项」挑不出来，
输出「这些义项都不贴合本句」——而义项里明明就有贴合的。既然模型自己会翻译，
直接让它「结合句子解释这个词 + 翻译整句」既短又更贴语境，`senses` 参数整个删掉
（前后端签名同改）。副产品：词卡上的 ✦ AI 不再依赖词典查到义项，查不到也能问。

**2. 空回答必须说清是哪种空。**
用户报的「AI 没有返回内容」在旧代码里是所有失败共用的兜底文案，而真实原因往往是
`finish_reason=length`（拆句的 JSON 很长，1024 max_tokens 不够；推理型模型的
思考也会先吃掉预算）或模型只填了 `reasoning_content`。现在 `ai.Reply` 带回
`finish_reason / usage / reasoning_content`，错误分成四句：
被截断、只输出思考过程、`content_filter` 等其他 finish、真的空回答。
`DefaultMaxTokens` 提到 4096（上限而非目标，不多花钱）。
另：截断的 JSON（`{` 开头但没有右括号）不再当散文硬展示，按「截断」报错。

**3. 本机诊断日志（`internal/logx`）。**
AI 出错依赖一个开发者摸不到的服务商，没有记录的话 bug report 只能是一句
「它没反应」。所以：内存环形缓冲 300 条 + `logs/app.log`（**上限 50 MB，超过就删掉
最早的 30 MB**，切在行边界上并写一条裁剪记录），
记录每次 AI 请求（system/user 全文、模型、baseUrl)、回答（finish、耗时、token、
正文）、空回答的原因、缓存命中、设置保存、前端 JS 错误与每次路由跳转。默认开启
（出事时关着的日志等于没有），可在「设置 → 诊断日志」关闭/清空/查看/复制，只在本机，
不上传。开关存 `logs/logging.json`，不写进 `config.json`（那份是要跟着备份走的）。
跨端：桌面 v2 绑定与手机 v3 `Call.ByName` 都自动带上新方法。

**为什么是 50 MB 而不是 512 KB 轮转一代。**
512 KB 只够一次会话——「昨天还好好的」这种报告就没法查了。手机上一个几十 MB 的
文本文件不算事，而诊断价值随时长增长，所以改成「长得下就一直留着」：写满 50 MB
才裁一次，裁掉最早 30 MB、留约 20 MB，裁剪频率极低（一次裁剪要再写 20 MB 才会再来
一次），也不会出现「刚出事的那一刻恰好被轮转掉」。裁剪在行边界上切，否则尾部
残留半行 JSON，`loadTailLocked` 会把它当坏行丢掉——那才是真丢数据。裁完在文件里写
一条 `日志超过上限，已删除最早的部分`（带 droppedBytes/maxBytes/trimBytes），
免得事后看日志的人以为文件是从半截开始的。

**4. 返回手势的哨兵改成「全栈一个」+ 延迟到提交后丢弃。**
黑屏的根因不在阅读器，在 `backNav`：原实现每个浮层压一条历史哨兵，卸载时靠
`history.state` 判断「刚才那下 pop 是不是我自己的」。词卡 → AI 面板这种嵌套栈里，
两个浮层会互相丢掉对方的哨兵；下一次返回于是 pop 掉一个真实页面条目，守卫为了
关浮层把这次 pop 吞掉，URL 和画面从此错位——再划几下就得到「白/黑屏 + 再按退出」。
现在：**打开多少浮层都只压一条哨兵**，栈空时才丢；丢弃延到 effect flush 结束后的
微任务（这样「关词卡 + 开面板」同一提交里不会误丢），且只在
`history.state.__backGuard && location.href === 压入时的 URL` 时才 `history.back()`
（多一道导航守卫：绝不在别人导航的途中倒车）。另外补了两道兜底：`ErrorBoundary`
（未捕获的渲染错误原来会把整棵树卸掉、只剩深色背景 = 用户说的黑屏）与阅读器分支的
`path="*"` 重定向到书架。回归：`backstack.cjs` 15/15。

**4b. 哨兵不许被「埋」——回退序列重复页面的根治（2026-10-26 追加）。**
上面那条只修了「哨兵互相丢」。用户随后报的序列是
**生词本 → 书籍正文 → 生词本 → 书架 → 退出**：浮层开着的时候应用内导航（AI 面板
的「去设置」，当时还有阅读器底部操作栏的「整理」——那个入口后来在手机端整体摘掉了，见
ADR-16）会 `pushState` 一条**真实页面到哨兵之上**，哨兵就被
埋了——`history.back()` 再也够不到它。下一次返回先 pop 掉这个被埋的副本（它的 URL
是上一页），路由照着它重渲染，于是用户"回到"了刚刚离开的正文；再下一次才真正退一层。
判据只有一条：**带 `__backGuard` 标记的条目永远不是页面**。四条规则：
1. 哨兵在顶上时，`history.pushState` 一律转成 `replaceState`（补丁装在
   `installBackGuard` 里）——假条目就地变成真页面，一层一次按键，且不会堆积。
2. 应用内「返回」按钮（阅读器 `goUp`、`SubHeader`）先 `closeForNavigation()` 关掉浮层，
   再按 `navigationDepth()` 退 1 或 2 层，并用 `leaving` 标记让那一次 pop 原样交给路由。
   修之前只退 1 层 → pop 撞上哨兵 → 守卫把这次 pop 吞掉去"关浮层" → 屏幕上什么都没发生，
   按钮看起来是死的（真机实测：词卡开着点「书架」，`history.length` 一动不动）。
3. 万一还是踩到一条没人认领的标记条目（旧版本残留、竞态），按「跳过」处理：
   `stopImmediatePropagation` 不告诉路由，再 `history.back()` 一次——一次按键仍然只退一层。
4. 点在当前所在的 tab 上不再压一条同 URL 的副本（`MobileTabs` 用 `preventDefault`），
   否则那一下"什么都没发生"，之后才变成一次空按。
另：`liveSentinel()` 只在导航前/关浮层时判断标记是否还有效（`replaceState` 会把哨兵
就地变成真页面），**popstate 里必须看原始标记**——那一刻浏览器已经站到页面条目上，
"当前条目不是哨兵"正是正常状态。回归：`backstack.cjs` 22/22（新增：浮层开着导航不
增加条目、一次返回回到阅读器不留幽灵页、词卡开着点「书架」一次就退）。

**4c. 一级 tab 是兄弟，不是层级（2026-10-26 再次追加）。**
用户第三次报回退：「在生词本回退一定是到书架，再回退就退出；而不是在书架回退时又回到
生词本」。这次跟浮层无关，是 tab 本身：`NavLink` 每次切换都 push，于是
书架 → 生词本 → 书架 → 生词本 的历史成了 `[/, /vocab, /, /vocab]`。第一次返回落到第三条
（书架，看起来正常），**第二次返回落到第二条，也就是生词本的副本**——于是"书架返回
又回到了生词本"。判据：同一层级的页面不该在历史里出现两份。

规则按「位置」而不是「累加」：
1. 在根（`idx === 0`）点非书架 tab：push 一次，书架留在下面，一次返回就回到书架；
2. 在一级 tab 上点另一个一级 tab：`replace`，深度恒为 2，书架永远在生词本下面；
3. 从二级页点 tab（`idx > 1`，当前 tabbar 不画在二级页，属防御分支）：先折叠回根，
   再从根进入，保证同一条不变式；
4. 点书架 tab：`nav(-idx)`，直接回根——书架就是根。

另一处配套修正：`goUp` / `SubHeader` 的退层层数要 `min(navigationDepth(), idx + 1)`。
`idx` 只数「根之上」的条目，哨兵不占 idx 但占一层，所以原来的 `min(depth, idx)` 会把
「页面 + 哨兵」算成 1 层，`nav(-1)` 只 pop 掉哨兵、路由不动——修完立刻在 `backstack.cjs`
里复现成「词卡开着点返回书架，卡片关了但页面没退」。而 `go(-3)` 在身后只有两条时是
静默 no-op，按钮同样会"看起来是死的"。

回归：`backstack.cjs` 33/33（新增：生词本深度 1 / 书架 tab 回根 / 反复切换不堆副本 /
兄弟 tab 就地替换 / 一次返回必到书架 / 再来一次真正离开 / 二级页返回到所属 tab 后
tab 规则仍成立）。

**5.「词库未收录」不再是一句话的终点。**
用户报：词库未收录的词更该有 AI 帮助解析，而不是只提示未收录。这条和第 1 点的结论
其实是一回事的两面：第 1 点让模型不再依赖词典义项，但词卡的「未收录 / 未安装」分支
当时还是死路——连 ✦ 按钮都没有（漏改）。现在这个分支自己带一个全宽的
「✦ 让 AI 解释「X」」，并在上面一行说明**为什么**它查不到（人名、地名、专业词常不在
词库里），词库未安装时同样给：模型从来不需要词库。点它和点卡片底部的 ✦ 走同一个
`explainThis()`（关词卡 → 开面板 → 带整句），所以两条入口不会各自漂移。
回归：`dictmiss.cjs` 12/12（未收录有入口、按钮点名该词、点开词卡关闭、面板含释义/
译文/词性、请求带的是整句、词库未安装时入口仍在）。

## ADR-11 书架列表只传缩略图，封面不进列表

**问题。** 用户报「切页面慢，回书架尤其明显，要 delay 一下」。真机量化（40 本、
`ListBooks` 返回全部书籍）后确认不是架构缺陷，是一处数据体积失控：

| 指标 | 修前 | 修后 |
|---|---|---|
| 列表体积 | 16.5 MB（其中 16.4 MB 是 base64 封面） | 1.4 MB（全为缩略图） |
| `ListBooks` 耗时 | 1.5–2.1 s | ~220 ms |
| 书架渲染里 `setAttribute('src')` | 22 次 / 866 ms | 11 次 / 82 ms |
| 最长掉帧 | 1238 ms | 182 ms |
| 点 tab → 书架进 DOM | 1.19 s | 0.23 s |
| 阅读器 → 书架 | ~1.4 s | ~0.35 s |

因果链有三段，都在同一份数据上：Go 侧每次列表都把所有封面读盘 + base64；16 MB 的
JSON 过桥；WebView 把 12 个 ~400 KB 的 data URL 写进 `img.src`（每次约 39 ms）并解码
——而卡片只画 ~120×170 CSS px。

**决定。** 封面旁存一份 320×480 JPEG（quality 82，约 20–45 KB）：

- 生成时机：导入时、换封面时同步生成；老书（本改动之前导入的）由第一次
  `ListBooks` 顺手起一个后台 goroutine 补齐，**列表本身绝不生成**（否则页面加载会
  变成图像转码任务，老库第一次进书架要等十几秒）。
- `BookDTO` 分两种：`toBookListDTO`（列表：只给 `thumbUrl`）与 `toBookDTO`（单本：
  `thumbUrl` + `coverUrl`，编辑页/拆分预览要原图）。
- 缩略图为纯标准库实现（`image` + 手写 box filter），不引第三方依赖；`golang.org/x/image`
  的缩放更好，但为一个小功能动依赖不值得。
- 解不出的格式（WEBP/AVIF/SVG）回退到原封面——那是少数几本的旧行为，而不是坏书架。
- 缩略图与封面同目录同名加后缀，跟着备份走，也不会进 `assets` 表（图片管理页看不到）。

**顺带修的两处同类问题**（都是「一次切换的总时间」的组成部分）：

1. **双指缩放等待 292 ms。** 全站只有 `.book-card` 设了
   `touch-action: manipulation`，tab bar 没设，WebView 在 touchend 之后压着 click
   不放（实测 touchend 457 ms → click 749 ms）。规则提到 `html`，读者自己的拖拽面
   仍用更严格的 `touch-action`（翻页 `pan-y`、选区手柄 `none`）。
2. **回到书架必然重绘一次。** 每次挂载都会重新 `ListBooks`，答案通常和缓存一模一样，
   但新对象身份让 12 张卡连同 12 次图片解码重跑一遍。`sameShelf()` 比对卡片真正画的
   字段（含 `thumbUrl`，因为换封面必须重绘），一致就保留旧数组。

**回归：** `library` 缩略图测试 6 条（尺寸/色彩/体积/复用/不可解码回退/列表只带缩略图）、
`shelfperf.cjs` 4/4（卡片用缩略图、无缩略图回退原图、无图显示书名、列表未变时封面只写
一次）、`mobile.cjs` 184/184、`backstack.cjs` 33/33、`ai` 64、`logview` 18、
`dictmiss` 12；真机 `device-hyphen` 7/7、`device-highlight` 5/5、`device-sel-ai` 4/4、
`device-tabs` 7/7、`device-back` 11/11、`device-leavebtn` 2/2。

## ADR-12 AI 对话是「记录」，不是新能力

**问题。** 0.4 的三个 AI 能力都是一次性的：问答结束，面板关掉，除了 `ai_cache` 里的
答案本身，什么也没留下。读者想「刚才那个词的解释里，它为什么说这是被动？」时，既回不
到那次对话，也没法接着问。

**决定。** 每次成功的 AI 回答都落成一条**对话记录**（`ai_conversations` +
`ai_messages`，role 含 `system`），并把「一次查词＝一次对话」写进定位：

- **记录的是真实通信内容，不是摘要。** 系统提示词作为一条 `system` 消息入库，页面上
  以折叠块完整展示。理由很直接：如果对话页只显示「问题 + 回答」，它就是对通信的复述，
  而不是通信本身；一旦回答跑偏，缺的正好是决定它跑偏的那段提示词。
- **一次提问一条记录，靠 `cache_key` 去重。** 记录时先按 `kind + sha256(prompt)` 查
  是否已有对话，命中就不再写。同一个词在同一句里被反复点开（滑词、误触、重看）不会
  堆出十条一样的记录，而提示词改版（键变了）会自然产生新对话——那是应该发生的。
- **继续对话 = 把存下来的消息原样发回去。** 不做「摘要前文」这类优化：这些对话很短
  （一次查词 3 条消息），而摘要会改变模型看到的上下文，让「继续」变成另一个问题。
  多轮能力落在 `ai.AskMessages` 上，`Ask(system, user)` 成为它的两消息特例。
- **失败的发送回滚自己的提问。** 发送时先落 user 消息再请求；请求失败或空回答就把那
  条 user 消息删掉。否则重试会留下两条一模一样的问题，而记录本该只说发生过什么。
- **词卡读缓存，绝不因此联网。** 卡片打开时问一次 `AIExplainCached`（只查
  `ai_cache`）：命中就把释义直接铺在词条下面（`词库未收录` 时则替代它），未命中保持
  原样。卡片是读者点开一个词的顺手动作，不该因为「顺便查一下有没有 AI 释义」而变成
  一次网络请求或一次等待。
- **对话进底栏（第四个一级 tab）。** 书架 / 生词本 / AI / 我的 是同级视图，沿用

## ADR-13 对话页的界面裁决：记录要能读，页面要能长

**问题。** ADR-12 把每次 AI 回答落成一条对话，页面照原样展示。四个问题随之而来：正文里
的 JSON（提示词要求的格式，也是模型真正返回的东西）在气泡里是一堵标点；一条对话打开后
只能看，回不到产生它的地方；输入框跟着内容一起滚，两个回合之后就得往下翻才找得到；列表
一次拉全部、每行挂一个红色「删」，读起来像数据库后台。

**决定。**

- **JSON 是「视图」，不是重写。** 气泡里能解析成对象/数组的内容按事实排版（键映射成中文
  标签：meaning→释义、segments→句子拆解…），列表就是列表，嵌套对象就是块；被一句话包着
  的 JSON（`结果如下：{…}`）也拆出来，前后的散文留在原位；原始对象收在折叠的「原始 JSON」
  里。**存的仍然是模型返回的原文**——排版只发生在渲染侧，否则对话就不再是通信记录，而是
  对通信的润色。
- **一级 tab 不画回退箭头。** 书架 / 生词本 / AI / 我的 是兄弟（`MobileTabs` 已定死兄弟
  语义），`/ai` 上面没有层级，箭头只会把读者带出 App。`/ai/:id` 才是栈在列表之上的页面，
  它保留箭头。判据是「这个页面有没有上一级」，不是「是不是二级页」。
- **列表分页，滚动续拉。** `AIConversations(offset, limit)` 返回 `{items, total, hasMore}`，
  默认 30、上限 100。列表是滚动浏览，不是导出；一页游标用 offset 成立，是因为排序键
  `updated_at` 每行唯一（追加时会往前推一格），页边界不会跳过或重复。续拉时仍按 id 去重
  ——列表打开期间新落一条对话，offset 的语义就漂了。
- **删除是手势。** 每行一个「删」占着拇指落点，也把阅读列表画成了管理界面。左滑露出删除，
  且**先判定轴向**（6px）：纵向滑动原样交还给列表，否则列表会在拇指下「卡住」。删除按钮
  默认 `opacity: 0`——只靠位移挡不住卡片圆角处漏出的一角红色。
- **输入框钉在底部。** `.ai-room` 占满一屏，消息区自己滚（`overflow-y: auto`），composer
  `flex: none`。滚动容器是消息区而不是整页，`scrollIntoView` 也就不会顺带把页面容器拖走。
- **答案自带回到记录的入口。** 词卡的缓存释义和 AI 面板的三种回答都带上 `conversationId`
  （拆句/导读此前丢掉了 `recordConversation` 的返回值），于是「眼前这段摘要」和「完整记录」
  之间只隔一次点击。

**代价与边界。** JSON 视图只处理对象/数组；一段既不是纯 JSON、又只坏在中间的回复仍按文本
显示（原文还在「原始 JSON」里）。左滑删除在桌面端要靠鼠标拖拽，键盘用户没有等价入口——
这是本轮接受的取舍，真需要时在详情页补一处删除即可。

**列表预览也要说人话。** 行内预览取的是「最后一句」，而最后一句是 JSON，于是列表上会出现
`{"summary":"…`。预览在 Go 侧取 meaning → summary → translation 里第一个非空的字段（都不
认识就取对象里第一个字符串），换行折叠成空格；对话本身仍然存原文、显示原文可折叠。

**回归：** `aichat` 新增 2 条（分页页边界不重不漏 + Total、预览去 JSON 外壳）、`app` 新增
3 条（分页 items/total/hasMore、默认页与上限夹取、拆句/导读返回对话 id）；浏览器
`aichat.cjs` 40/40（无回退头、首页只取 30 条、滚动续拉到 32 条且不重复、预览无裸 JSON、
JSON 结构化且原文可折叠、composer 底部固定且不随滚动移动、词卡与面板跳转对话、左滑露出
删除且滑动不误触发导航、删除后总数跟随），回归 `verify` 19/19、`mobile` 184/184、
`backstack` 33/33、`ai` 64、`dictmiss` 12、`esc` 24、`drop` 21、`shelf` 20；真机
`device-aipage` 20/20（一级 tab 无回退箭头、详情页有、真 JSON 渲染成「摘要/要点/术语」、
composer 贴底且长对话自动滚到末尾、左滑露出删除、滑动不误开对话、竖向滑动不劫持列表、
再点一下收回）、`device-tabs` 8/8。

## ADR-14 生词卡：词是主角，句子是证据

**问题。** 生词本一行点下去是**跳正文**，回答的是"这词在哪"而不是"这词是什么"；一次翻页
之后读者还站在章节另一头，得自己走回来。更糟的是例句本身：`sentenceAt` 在词的左右各数
220 个字符就停，那不是句子，是句子的半截——*Lessons in Chemistry* 开篇一句 583 字符
（分号连缀），实机上存下来的正是 `esses and joined garden clubs … the thirty-year-old
mother of Madel`：开头半截单词、结尾半截单词、没有句号。行内又用 `-webkit-line-clamp: 3`
裁三行，普通长度的句子也读不全。

**决定。**

- **例句走到段落尽头，只在没有句末标点的块里开窗。** HTML 没有"句"这个概念，只有"块"，
  所以扫描边界就是词所在的段落；砍掉 220 上限后，一句 583 字符的话就是 583 字符。真正的
  极端情况（诗、连排对话、被压成一个 `<p>` 的表）走窗口：以词为中心取 800 字符，**切在
  空格处**（CJK 没有空格，40 字符内找不到就按字切，这在中日文里是正常断行），被切的一侧
  补 `…`——半句话至少看起来像半句话。
- **`…` 是标记，不是内容。** 带省略号开头的一律视为"已经尽力切过"，不再进入重切流程
  （否则每次开生词本都会为它渲染一次章节，结果还是同一个字符串）。
- **旧记录自愈。** `looksLikeFragment` 多一条判据：**结尾不是句末标点**（允许后接引号/
  右括号）就算片段。旧上限切出来的行大多结尾停在半个词上，打开生词本时 `repairContexts`
  就用今天的规则重切并写回；仍守着"新的必须更长、必须还包含这个词、offset 必须还落在词
  上"三道闸，过不了就原样留着。
- **点词开卡，跳正文降级为卡片里的一个动作。** sheet 里是：词 + 音标 + 发音、释义、**整句**
  （不裁）、出处与排程、`查过/复习/忘过` 次数，底部两个按钮——`定位原文` 与 `✦ AI 解释`。
  AI 用的是「这个词 + 这一句」，与阅读器词卡同一条 `ExplainInContext`，也共用缓存与对话
  记录，所以同一问题在哪儿问都命中同一条答案。曾经问过的，答案直接躺在卡片里。
- **行内保留预览，但放宽到 5 行。** 三行连普通句子都切，五行能容下大多数；真正长的交给
  卡片——列表是扫视的，卡片是阅读的，两者不该互相将就。

**代价与边界。** 行会变高（40 行的列表比原来长）；没有原句的老词条不能问 AI（按钮禁用并
说明原因），因为 `ExplainInContext` 必须有句子才有可能回答；重切依赖章节还能渲染——书删了
就修不了，卡片里的原句保持原样。卡片里的 AI 会把上下文发出去，这一点与阅读器词卡一致，
仍然只在点击后发生。

**回归：** 浏览器 `vocabcard.cjs` 17/17（查词取到完整 583 字符句、偏移与章节一致、列表 5 行、
旧 446 字符片段被重切并写回、点行停在 `/vocab` 且开卡、卡片原句完整且标出词、两个动作都在、
卡片里能查 AI 并带「查看完整对话」、关面板回到卡片、定位原文进正文）、
`sentence-window.cjs` 4/4（无句末标点的 3600 字符块开窗到 793 字符、两侧省略号、不从词中间
切、含目标词）；回归 `mobile` 185/185（新增「点行开卡且不离开生词本」一条）、
`vocab-schedule` 15/15、`backstack` 33/33、`verify` 19/19、`shelf` 20/20、`hyphen-hit` 10/10、
`dictmiss` 12/12、`esc` 24/24。

**补记（同日，真机复核后）：完整句「存」下来是必须的，「显示」它不必一次摊完。**
583 字符的句子放进 AI 面板后，`在本句中` 的释义正好落在屏幕最下一行——面板本来是来解释
这句话的，结果第一屏全是这句话。现在 `.ai-sentence` 超过 240 字符就折成 4 行（`AISentence`
组件，`is-folded` + `-webkit-line-clamp`），下方一个 `展开整句` 按钮原地展开/收起。

- **折叠是视图，不是数据。** DOM 里的文字一直是完整的（`textContent` 583 字符不变），
  只是视觉裁切；生词卡下面的 sheet 本来就完整显示整句，所以"少看"的那部分在同一个屏幕的
  下一层。
- **阈值 240 而不是"永远折"**：阅读器里普通句子 100–200 字符，折了只会多一次点击，没有
  收益；只有真正长的句子（文学长句、分号连缀）才折。展开按钮只在长的时候渲染。
- 真机实测（`probe-ai.mjs`）：折叠后释义 `offsetTop = 482`（视口 758，第一屏可见）；
  展开后 745，又回到边缘——说明这一折确实换回了答案的位置。

**回归补记：** `vocabcard.cjs` 21/21（新增折叠 4 行、`展开整句` 可点、展开后文字 583 字符
且 `scrollHeight == clientHeight`、答案没被挤掉）；真机 `device-vocabcard` 12/12 复跑通过，
`probe-ai` 3/3（答案真的到达、折叠生效、可展开），AI 回答在手机上实测命中缓存并完整译出
583 字符的整句。

**补记二（同日，约翰的要求）：卡片底部的动作是链接，不是按钮；查词历史也有这样一张卡。**

- **两个动作改成文字链接。** `.vocab-sheet-actions`（`.btn` 撑满两栏、44px 高、主按钮填充色）
  换成 `.vocab-sheet-links` + `.vocab-sheet-link`：无边框无底色、accent 色、`padding: 6px 0`
  撑出 32px 点击高度（真机量 `56×23`→点击盒 `56×32`）。理由不是审美：这张卡的主角是那句话，
  底部一颗填充色的主按钮把"离开这里"变成了全卡最重的元素，读者点它比读句子更容易。
- **已经问过的词不再给 AI 链接。** 答案已经印在卡片里（`.dict-ai`），再给一个通向同一个答案的

- **没有句子就没有 AI 链接。** 之前是禁用按钮 + title 说明，但禁用的文字链接和普通文字长得一样，
  点了没反应更困惑；现在直接不渲染。
- **`WordSheet` 抽出共用的壳**（词 + 音标 + 发音 + ✕ / 滚动正文 / 链接页脚 / overlay 槽），

- **`whenLabel` 挪进 `vocabLabels.ts`**：行和卡都要说"查过 3 次 · 昨天"，同一个日期不能有两种说法。

**代价与边界。** 加词从"列表一击"变成"列表一击 + 卡内一击"；历史卡比生词卡更空（只有词、释义、
时间、一个链接）——它是"确认这个词是什么"的最小面，不是阅读面。列表不再有任何按钮，可点性靠
`note-card-main` 的悬停/按压反馈，与生词本一致。

## ADR-15 浮层的位置由它自己的尺寸驱动

**问题。** 阅读器三类浮层（选择工具条、词卡、批注小窗）都是 `position: fixed`，位置由
`placeOverlay(锚点, 尺寸, 视口, 偏好侧, 间距)` 算出来，尺寸取 `offsetWidth/offsetHeight`。
问题出在「尺寸」是一个**瞬间快照**：词卡打开时先按「词典条目」的高度摆好，随后缓存里的
AI 释义异步到达（同一个词第二次点开就是这条路径），卡片高度翻倍 —— 真机实测 `217 → 424`，
而位置还停在旧高度算出的 `478`，下沿落到 `902`，视口只有 `758`：最后几行（也就是读者点
开的那个答案）在屏幕外，正是约翰截图里的样子。原来那道保险是 `revision` 参数，靠手写状态
键（`found-recorded`）触发重算；缓存释义到达时这个键不变，所以永远不会重算。

**决定。**

- **尺寸变化由元素自己报告，不由状态键列表猜。** `useAnchoredOverlay` 在 `useLayoutEffect`
  里挂一个 `ResizeObserver` 观察被测元素，任何让高度/宽度变化的因素都会重新摆放：缓存释义
  到达、字体切换导致换行、图片加载、「加入生词本」变成「已在生词本」。`revision` 保留（它
  处理的是「尺寸没变但位置该变」的情况，成本为零），但不再是唯一的触发器。
- **长高要把卡片往上推，不能往下淌。** 侧向选择原来只有两条路：偏好侧放得下就放，否则
  另一侧放得下就翻过去，都放不下就钳在偏好侧。**钳**意味着卡片扣在自己解释的那个词上
  （真机：词在 444，卡片盖住它）。现在第三种情况改成「哪边空间大去哪边」：同一次真机
  复现，卡片停在 `8..432`，词留在下面可见。
- 钳位本身保留：卡片高于视口时仍然贴着上边缘显示顶部，并且 `.dict-card` 自己的
  `max-height: 62vh` + `overflow-y: auto` 保证放不下的部分能滚动读到，不是被裁掉。
- **不用「等内容都到齐再显示」来回避跳动。** 那会让每一次查词都等一次 IPC + SQLite 查询，
  而跳一次（`478 → 8`）发生在打开后的百毫秒内、读者还没开始读，代价比延迟低得多。

**代价与边界。** 卡片高度变了就可能位移，读者若恰好在那一瞬间按住卡片拖动，会感觉位置跳
一下（真机上发生在开卡后 ~150 ms 内，尚在「刚打开」的心理窗口里）。`ResizeObserver` 在
每次尺寸变化时调用 `measure`，因此要求 `placeOverlay` 的计算不改变元素尺寸（当前实现只写
`left/top`，fixed 定位下不影响布局），否则会成环。三类浮层共用这套逻辑，所以批注小窗、
选择工具条也一起吃到了这个修正。

**回归：** 浏览器 `cardplace.cjs` 14/14（无标点长段落里把词停在 84% 高度、缓存释义到达后
卡片从 217 长到 424 仍整体在视口内、底部距边 8px、且**落在词的上方而不是盖住它**；词在页面
顶部时仍然向下展开；没有缓存释义的卡片位置不变）；真机 `probe-cardplace` 13/13
（Taboo 第一章 `personalities`，卡片 478..695 → 424 高后停在 8..432，下沿 432 < 750，
滚动到底仍在屏内）；回归 `mobile` 192/192、`ai` 64、`backstack` 33、`esc` 24、`dictmiss` 12、
`hyphen-hit` 10、`shelf` 20。

## ADR-16 手机端不提供「整理」，只保留书籍元数据编辑

**问题。** 阅读器底部操作栏是五个槽位（目录 · 书签 · 划线 · 整理 · 设置），「整理」跳到桌面端
的三栏章节编辑器（拖动章节排序、改章节 HTML、把一本拆成多卷）。真机上它是这一排里唯一一个
把读者带离阅读、而且进去之后**没有任何控件是按手指设计的**入口：拖动排序要精度，编辑器要横向
空间，拆分要一眼看见整本书的章节树。用户的判断很直接——「实用性太差，整体摘掉」。

**决定。**

- **手机端底部操作行变成四槽**（目录 · 书签 · 划线 · 设置）。判据是「这个动作能不能只用拇指
  完成」，不是「功能重不重要」：留下的四个都是就地弹出底部面板的单手动作。
- **手机端保留的编辑是书籍级元数据**（书名 / 作者 / 标签 / 封面），入口是书架长按封面弹出的
  面板（v0.3 就有）。这次只是把「整理」的位置让回给它，不是新增一个能力。
- **光摘入口不等于摘掉**：`/books/:id/edit` 路由本身在 touch-primary 设备上回答一张说明页
  （「整理功能只在桌面端提供」+ 指回长按编辑 + 返回书架）。同一条 URL 还能从旧链接、升级前
  留下的历史条目进来，那时候把手机丢进桌面布局就是「点一下就进了个没法用的页面」。
- **桌面端一处不减**：滚动模式工具条、书架卡片、`/books/:id/edit` 都还在。（桌面默认是翻页
  模式，`整理` 一直挂在滚动模式的工具条上，这次没有动。）

**代价与边界。** 手机端从此不能改章节标题 / 正文、不能拆分、不能导出——这些回桌面做。书籍级
那四件是手机上唯一的编辑面，所以它的入口必须说人话：长按 500 ms，菜单项直接列出四个字段，
而不是含糊的「编辑」。

**回归：** 浏览器 `organize-mobile.cjs` 12/12（四槽且无「整理」；四槽等宽不溢出、栏体仍贴在
底部全高；旧链接落到说明页且编辑器零节点；说明页指回长按；书架卡片按钮在手机上不可见；长按
仍能改四件；桌面滚动工具条与书架卡片仍有「整理」，桌面 `/edit` 仍渲染编辑器）；`mobile`
192/192、`backstack` 33/33、`bookmark-once` 11/11、`verify` 19/19。

## ADR-17 批注是选区工具栏上的动词，不是划完之后的追问

**问题。** `note` 字段从第一天就在（`AddAnnotation` 收它，`UpdateAnnotation` 改它），批注
小窗也能写 —— 但入口藏在「点已有划线」后面。结果是一条划线带一句想法要两步：先点色块划上，
再回到那一句上点开小窗。读完一段正想写两句的时候，手指离开选区的那一刻想法还在，点开小窗
的时候它已经散了；手机上更糟，划线是长按选词、写批注是另一轮手势。用户的话很直接：
「划线时，可以添加笔记」。

**决定。**

- **批注是工具栏里的第三个动词**，和查词、✦ AI 并列，排在色块前面（三个是动作，三个是
  样式）。一次按压做两件事：按**上次用过的颜色**划上，并把光标放进批注输入框。
- **颜色沿用 `markColor`，不重置成黄。** 一个正在用绿色标重点的读者，写批注时不该突然
  得到一条黄色的划线 —— 那条划线会看起来像另一个人划的。
- **复用同一扇小窗，不做第二个编辑器。** 点已有划线打开的是同一个 `.ann-popover`，
  `fresh` 只标记「这条是刚划的」，用来决定要不要把光标放进输入框。写批注的路径和小窗
  的既有能力（改色、删除）天然叠在一起：划完发现自己选错颜色，直接点另一个色块。
- **只有 `fresh` 才自动聚焦。** 点已有划线是为了改颜色时，键盘不应升起 —— 那会盖住读者
  正在看的那一页，而他要做的事和输入无关。
- **小窗顶部回显被划的句子（`.ann-quote`，两行截断）。** 手机上小窗就浮在那句话上面，键盘
  一升，那句话整段被盖住；不把它拣出来，写下的批注就是对着一片空白写的。桌面上这行同样
  有用：改了颜色的划线，靠它确认改的是哪一句。
- **只在翻页模式提供。** 高亮本来就只由翻页视图绘制，滚动模式下没有划线可挂批注。
- **术语统一成「批注」。** 用户说的是「笔记」，但列表页、手机划线面板、保存后的提示从 0.2
  起都叫「批注」（`批注：…` / `已保存批注`），再造一个同义词只会让人以为这是两个功能。
- **空批注保存 = 普通划线**，不报错：按了批注又改主意，留下的应该是一条划线，不是一条
  需要解释的错误。

**一个只在实现里才看得见的坑。** 自动聚焦必须**延后一帧**：`useAnchoredOverlay` 的浮层在
测到自身尺寸之前以 `visibility: hidden` 挂载（ADR-15），而**隐藏元素无法获得焦点** ——
在 `useEffect` 里直接 `focus()` 会静默失败，`document.activeElement` 仍是 `BODY`。真机上
这一帧的差别就是「点了批注，键盘不弹」。`requestAnimationFrame` 之后再 `focus()`，
`selectionStart` 放到末尾（批注是往后写的）。

**代价与边界。** 工具栏在手机上从 5 个控件变成 6 个（查词 / ✦ AI / 批注 / 三色块）：真机
360px 下整条 `8..303`，`批注` 自身 `52×30`，没溢出、没缩到点不中。点了批注却不写字直接
关掉，划线保留、批注为空 —— 和先划线再加批注的结果完全一样，所以这条路径不会产生第二种
状态。

**回归：** 浏览器 `annotate-note.cjs` 21/21（工具栏有批注且排在色块前；一次按压划线并打开
输入框、光标在框里、小窗回显原句且完整在屏内；保存写进那条划线；点已有划线**不**抢焦点；
下次批注沿用上次颜色；空批注保存不报错；滚动模式没有批注）。**反证**：把颜色写死成 yellow、
把聚焦改成直接 return，`with the cursor in it` / `the next 批注 uses the colour last marked
with` / `and the keyboard is raised for the note` 三条立刻变红。真机 `device-note.mjs` 12/12
（长按选词 → 点批注 → 里程碑：`mark.hl` 出现、`activeElement` 是 `.ann-note`、视口
`758 → 479` 即键盘真的升起、小窗下沿 `432 < 479` 没被键盘盖住、输入内容写进数据库
`note` 字段、保存后键盘收起）。回归 `mobile` 192、`verify` 19、`hyphen-hit` 10、`esc` 24、
`ai` 64、`backstack` 33、`cardplace` 14、`vocabcard` 24。

## ADR-18 「停在屏幕外」必须靠裁剪，不能靠合成层的边界

**问题。** 跨章**前翻**完成后，上一章的内容会闪一帧。稳定态是干净的（截图、逐帧
`caretRangeFromPoint` 都只看到新章），所以它不是布局错了，而是某一帧被画了出来。

**根因。** `TurnPeek` 里装的是**整章的列条**：`.turn-peek-columns` 的宽度 =
`列数 × 列宽 + 列间距`，390px 视口下实测 **4790px**；而 `.turn-peek` 自己只有一屏宽
（正好一个跨页，`viewWidth`），靠 `translate3d(±stride)` 停在屏幕外。它**没有裁剪**，
所以列条会从盒子外面伸出来：

```
侧向   peek 盒子        列条范围            与视口（0..390）
+1     [404, 794]      [426, 5216]        不相交
-1     [-404, -14]     [-4422, 368]       压住 0..368   ← 上一章的最后一页
```

桌面浏览器看不出来，是因为**提升为合成层的元素会被按层边界裁掉**（`will-change:
transform` 带来的层），这不是我们写的规则。真机 WebView 在层刚建立的第一帧并不总是
遵守它，那一帧就把列条画在正文上 —— 上一章最后一页，闪一下，然后层裁剪接管，又消失。

**为什么只有前翻跨章会闪。** 停在某章第一页时（`pageIndex === 0`）预取的方向是
**前一章**（`side: -1`），列条的溢出正好回扫屏幕；停在末页时预取的是**下一章**
（`side: +1`），溢出朝右，本来就够不到视口。

**决定。** `.turn-peek { overflow: hidden }`。peek 的语义就是"一屏大小的画框，里面放着
相邻章节的某一页"，超出的部分从来不该被看见，也不该被命中。裁剪写进样式之后，"停在
屏幕外"变成一条**我们声明的**规则，而不是合成器心情的副产品。盒子宽度等于跨页宽，
双页模式下第二页也在框内，不会误裁。

**为什么原来的测试抓不到。** 断言查的是 `.turn-peek` 自己的 `getBoundingClientRect()`
——它在屏幕外，一直都是。没人查它**里面的列条**；而桌面截图又是干净的（层裁剪）。
新断言问的是裁剪之后的问题：**命中测试**，`elementFromPoint` 在屏幕中心，临时把 peek 的
`pointer-events` 放开一次（它设计上是 `none`，否则永远命中不到）。修复前这条报
`peek strip -4422..368, sheet 0..390`，修复后通过。反证：删掉 `overflow: hidden`，
两处里在左侧的那条立刻变红（右侧那条本来就通过，它测的是另一半）。

**边界。** 这条裁剪也让 peek 的"不响应触摸"更彻底：以前 `pointer-events: none` 挡的是
事件，现在连可见区域都不出框。拖拽时 peek 在 0 位，框内正好一屏，显示不受影响
（`pageturn-chapter` 仍 29/29，含"逐帧没有任何一帧露出空白纸面"）。

**回归：** `pageturn-chapter` 29/29（新增两条命中测试）、`pageturn-drag` 31/31、
`mobile` 192/192、`verify` 19/19、`backstack` 33/33。

**附记（同日，双页模式的后续）。** ADR-18 的裁剪验证顺手暴露了双页模式的另一个老问题：
翻页上限是 `pageCount - pagesPerView`，强制每个跨页都满员 —— 9 页的章节在宽窗口下只会
翻到 1 / 3 / 5 / 7，然后直接进下一章，第 9 页对读者不存在。奇数页数才是常态。上限改为
**最后一个有内容的页对齐索引**（`⌊(pageCount-1)/ppv⌋·ppv`），最后一个跨页允许只有一个
页面，像一本真实书的最后一页。孤页的纸张形状与页码角原按页码奇偶取左右 —— 满跨页时奇偶
与槽位一致，短跨页就反了（书脊朝左、页码贴沟）；改为**按槽位**取，单页模式不变。

## ADR-19 提示词是「开场时拷贝进对话的」，库不是事实源

**问题。** 自建对话的开场提示词是代码里的常量（`manualChatSystem`），读者改不了；而 AI 相关的
配置挤在设置页的一张卡片里，随着能力增多已经装不下。用户的诉求有三层：把 LLM 配置独立出来、
对话提示词可配置且可恢复默认、以及一个能按用途保存的提示词库，在自建对话里挑选使用。

**决定。**

- **LLM 配置独立成页**（`/llm`），三张卡按首次使用的顺序排：接口（地址/模型/密钥，BYOK
  不变）、对话提示词、提示词库。设置页只留一行入口——它首先是阅读偏好页。
- **提示词的解析顺序是三层**：新对话时**库提示词（点选）> 配置的自定义提示词 > 内置默认**。
  「恢复默认」就是存一个空串，不是又一个特殊状态。
- **库不是事实源。** 对话开始的那一刻，提示词被**拷贝**为转写的第一条消息——对话页展示的
  就是当时真正发给服务商的东西。之后改库、删库、改配置，都不回写已开始的对话。删除一个
  提示词只是让它不再被新的选择器提供。
- **选择器只存在于第一条消息之前。** 对话一旦开始，转写里已有它的提示词，中途换用会让记录
  撒谎；想换个提示词，开个新对话。
- **开场提示词随第一次回答一起回来**（`AIChatTurn.system`）。此前新对话的首屏只有问和答，
  读者选了提示词却当场看不见它生效了什么——下一次进页面才补上，这是把最重要的上下文当成了
  惊喜。

**边界。** 三个内置能力（查词 / 拆句 / 导读）的提示词**不开放定制**：它们的回答要过 JSON
解码器，读者改坏一句「只输出 JSON」就能让整个能力看起来坏了；而且它们的结果进了 `ai_cache`，
改提示词等于全体失效。可定制的是自建对话——那里的回答是自由文本，怎么引导都行。

**回归：** Go `aiprompt`（CRUD / 校验 / 截断 / 未知 id 静默 nil）、`aichat`（三层解析顺序、
恢复默认、转写保留出生提示词、未知 id 回退）、`app` 全量。浏览器新增 `llm-prompts.cjs`
15/15（设置页一行入口；三张卡；提示词卡的保存与恢复默认走独立接口；库的新增/改名/两段式
删除；选择器列出默认+库；点选的 id 随首条消息发送；转写首屏带出开场提示词、选择器消失）；
`ai` 64、`aichat` 40、`verify` 19、`backstack` 33、`mobile` 192。

## ADR-20 书的 markup 不许看见应用的 CSS：class/id 在 sanitize 时剥掉

**问题。** 有几本中文 EPUB，滚动模式一章很长，一切到翻页就只剩一页。用真实章节 HTML
逐层复现：纯 multicol 探针正常（两百多列），同一份 HTML 进了真 Reader 就塌成 `scrollWidth`
一列宽。差异不在测量时机、不在 CJK 断行，而在**类名碰撞**：txt 转制的书整章包在
`<div class="main">` 里，而应用外壳自己就有 `.main { overflow-y: auto }`。书的样式表
从来不加载，这个 class 唯一能做的事就是撞上应用的规则——撞上 `overflow` 就把整章变成
滚动容器，而 CSS 分栏里**滚动容器是整体块（monolithic），永不跨列切分**。十万个字符
全塞进第一列，`pageCount` 自然是 1。滚动模式没有分栏，div 照常长高，所以看起来一切正常。

**决定。**

- **class 与 id 在 sanitize 时剥掉**（`CHAPTER_PURIFY.FORBID_ATTR`）。书的 CSS 不加载，
  class/id 在阅读器里本来就是死重；它们唯一可能的效果就是与 `.main`、`.topbar`、`#root`
  这类应用类/ID 相撞。`display:flex` 的碰撞（撞 `.topbar`）和 `overflow` 的碰撞（撞
  `.main`）都能把一章压成残页，这类属性恰恰是阅读器**不敢**全局强改的（`display` 一改
  行内流全毁），所以必须在入口处让它们根本进不来。
- **行内 style 是第二道门，用 CSS 挡**：`.reader-content` 子树 `overflow: visible
  !important; position: static !important`。`<div style="overflow:hidden">` 包整章的书
  真实存在，行内 style 过不了 sanitize 这关，只能在渲染层抵消；而 `!important` 恰是
  行内 style 也压不过的少数手段之一。应用注入进正文的东西（高亮 mark）不需要这两个属性，
  `jump-flash` 等浮层都在 `.reader-content` 之外。
- **offset 不受影响**：剥的是属性不是文本，渲染文本的字符流逐字符不变，划线/进度/书签/
  生词的指针全部原样有效；`chapterHost`（查词/拆句的解析）走同一份 `CHAPTER_PURIFY`，
  两侧看见的仍是一样的 markup。

**反证（两道防线各有牙）。** 去掉 CSS 加固：`overflow:hidden` 行内样式的章节立刻塌回
1122px（一列）。恢复 CSS、只去掉 `FORBID_ATTR`：`overflow` 碰撞被 CSS 挡住（律师娇妻
保持 91422px），但 `class="topbar"` 的 `display:flex` 碰撞塌到 8948px 且内容压坏——
证明剥 class 不是 CSS 加固的冗余，而是挡住了 CSS 不敢碰的那一半。

**回归：** 复现脚本（真实章节体 + mock 后端，desktop + scroll→paged 转换两路径）：
律师娇妻 1122→91422、卡拉马佐夫 87208、俗人回档 137174、活着 139582，行内样式与
class 碰撞构造章全部正常分栏；`pageturn-chapter` 29/29、`pageturn-drag` 31/31、
`backstack` 33/33、`bookmark-once` 11/11、`annotate-note` 21/21、`sentence-window`
4/4、`hyphen-hit` 10/10、`mobile` 192/192、`verify` 19/19、`ai` 65。

## ADR-21 四个一级页共用一套骨架：固定的是「行」，不是页面

**问题。** 四个底部 tab 长得像一回事，行为是四套。书架把标题栏和列表拆成两个盒子
（`.page.library` 的列 + `.lib-scroll`），标题栏永远在；生词本用**同一个** `.lib-head`，
却直接跟在 `.page` 里，滚一下标题就没了；AI 列表靠 `.sub-head` 的 `position: sticky` 在
手机上顶住，桌面上照样滚走；我的连 sticky 都没有。书架自己也没做全：标签 chips 留在滚动区
里，标题不动、筛选跑掉——半固定。用户的话：「将四个一级页面的风格设计统一，参照首页书架的
设计，顶部标题栏和主操作行部分设计为固定，不随滚动条滚动」。

**决定。**

- **一个骨架类 `.page.shell`**：`height: 100%` 的列，`.lib-head`（标题栏）+ 可选的动作行
  + `.lib-scroll`（唯一滚动区）。四个 tab 都套它，`我的` 与 `AI` 从「没有固定」和
  「sticky 固定」改成同一件事。
- **行放在滚动区外面，不用 sticky。** sticky 要写死「上面那行有多高」，而这个高度会变
  （搜索框展开、计数变长换行）；两个数字一旦漂移，内容就从缝里透过去。column 里每行多高
  就是多高，滚动区永远从最后一行的下沿开始，没有第二个数字需要维护。
- **动作行 = 各页的 chips 行**（书架的标签筛选、生词本的 全部/待学/学习中/已掌握）。两行都
  出血到屏幕边（`margin: 0 -20px` + 同宽 padding）：否则长到屏幕外的 chip 会在 padding 线
  被切断，看着像列表到头了。
- **手机上标题栏强制一行**（`.page.shell > .lib-head:not(.search-open)`）：能换行的固定栏
  不是固定栏——它一换行，下面每一行都跟着下移。装不下的东西降级：次要动作变 38px 圆形图标
  （`.head-icon`），计数先省略（`.phone-only` 的短计数）。
- **生词本照抄书架的搜索交互**：放大镜 → 输入框整行展开（`.search-open`），而不是常年占
  一行输入框。
- **`.sub-head` 只留给二级页。** AI **列表**是 tab、没有上一层，改用 `.lib-head`（16.5px 的
  「系统栏」标题比书架矮一头，而它们本来就是同级）；对话页 `/ai/:id` 仍用 `SubHeader`。

**代价与边界。**

- **`.main` 在这四个页面上不再滚动**：滚动条从窗口右边挪到内容列右边（桌面 1180px 列）。
  这是书架的现状，现在四个页面统一。
- **滚动容器换人**：「滚到底加载更多」的 sentinel 仍在 `.lib-scroll` 里；IntersectionObserver
  用视口 root，被祖先 `overflow` 裁剪的元素照样判为不相交，行为与书架分页一致（书架一直这样）。
- **浏览器原生「点状态栏回顶」不再对这些页面生效**（它只滚 `.main`）。桌面滚轮不受影响，
  指针落在滚动区上就滚它。
- **手机端生词本头部从三行压成一行**，`查词历史` 由文字按钮降级为时钟图标（`aria-label`
  保留名字，`getByRole` 仍能按「查词历史」找到；桌面保留文字按钮，两者互斥显示）。

**真机（360×758 CSS px）补的三条。** mock 用的 390 宽把余量凑够了，360 宽的机器上这些
都在边缘上：

- **标题不许被压缩。** 生词本那一行（标题 63 + 计数 72 + 三个控件 + 复习按钮）合计 357px，
  差几像素就顶满，flex 让 `h1` 吸收了差额 —— 「生词本」被拆成「生词 / 本」，固定栏自己长到
  64px。现在 `.page.shell > .lib-head > h1 { flex: 0 0 auto; white-space: nowrap }`，**要退让
  的是计数**（`.tag` 省略号），不是标题。标题换行是这里唯一不可接受的失败。
- **手机计数不重复按钮上的数。** 复习按钮已经写着「复习 172」，计数再写「· 到期 172」既是
  重复也是压垮标题的那几十像素；手机端只留「172 词」。
- **搜索框在手机上排到最后。** DOM 里它排在按钮之前（桌面行里读作「左边输入、右边按钮」，
  顺序是对的），但手机上它 `flex: 1 1 100%` 占满一行，把后面的 🔍 / 🕐 / 复习 全挤到第三行
  —— 固定栏变成三行。`.page.shell > .lib-head > .input { order: 10 }` 让它落到第二行，
  头部一次只长一行（38 → 78），**收起后必须回到 38**。
- **两种状态的 `margin-bottom` 要一致。** 原来只在 `:not(.search-open)` 上写 12px，展开时
  回落到基础的 20px：头部长了 88px、滚动区只缩了 96px，多出 8px 的账。现在统一 12px，
  不变式是「滚动区的下沿不动」（它钉在 tab 栏上，头部吃掉多少就从列表里扣多少）。

**第二行只能有一套控件（2026-10-29）。** 骨架统一了「行在哪」，没管「行里是什么」，
于是三页各长了一套，用户一眼就看出来：「从首页切换到生词本，明显感觉到第二行比首页高了一点，
并且按钮样式也没有共享首页样式」。

- **chips 只有一套类名**：生词本原来的 全部/待学/学习中/已掌握 是 `.btn.sm`（26px 高、6px 圆角、
  行内无上边距），书架标签是 `.lib-tag-chip`（28px 高、999px 圆角、行内上边距 2px）——同一个位置，
  行高差 2px，看起来像另一个控件。现在书架标签、生词本状态、AI 来源全是 `.lib-tags` +
  `.lib-tag-chip`。**新加一类筛选就用这套类名，不要再造 `.xxx-filters`。**（`lib-` 前缀是历史：
  这行最早属于书架。）
- **搜索框尺寸只能定义一次**：`.input` 的 padding 给出 33px（书架、AI 用它），生词本自己写了
  `height: 32px` 得 32px，桌面端生词本整页因此比书架高 1px。现在由 `.lib-search-input` 统一
  220×32，三页的 `.lib-head` 高度、chips 行顶边、滚动区顶边逐像素相同（1280 与 360 都验过）。
- **筛选必须落在后端**：AI 列表是分页的（一页 30 条），在客户端过滤等于只搜已下载的那一页。
  `AIConversations(origin, keyword, offset, limit)`，keyword 同时匹配标题与消息正文（读者记得的
  往往是对话里说过的话，不是被截断成 12 字的标题）；换条件一律从 offset 0 重来，并用 seq 号丢弃
  上一条件的在途响应。chips 行用**未过滤**的总数决定显隐，否则筛出 0 条时连「全部」都一起消失，
  人就被困在空列表里。

**阅读器底部的触摸模型（真机确认，两条相反的状态）。**

- **chrome 可见**时整条 `.m-bottom` 是 `pointer-events: auto`（滑块要拖），所以压在 footer
  上的滑动不翻页、点击也不该有副作用 —— 实测：不翻页、不开词卡；上方滑块照常响应。
- **chrome 隐藏**时 `.chrome-hidden` 把整条设为 `none`，压在 footer 矩形上的滑动照常翻页
  （实测 transform 变化且页码前进）。这一条才是阅读时真正要紧的。

**全书百分比的真实口径（README 说过的那句话是错的，已改）。**
`progressPct = (章索引 + 页内比例) / 章数`，是**连续**估计而非按章跳：真机 70% → 71% → 73%，
同章每翻一页涨 1~2 个点；跨章 81% → 82% 不倒退，页码同时从 14/14 回到 1/11。因此「全书」
二字的作用是**分清分母**（本章页数 vs 整本书），不是「它按章算」。章被当作等长，所以它是
估计值。

**回归：** 四个页面在 390×844 与 1280×900 下滚到底，标题栏 y 坐标保持 20（桌面 76）不变；
`mobile` 193/193、`aichat` 43/43、`shelf` 20/20、`shelf-tags` 全通过、`vocab-schedule`
15/15、`logview` 18/18、`llm-prompts` 25/25、`organize-mobile` 12/12、`me-verify` 36/36。
真机 360×758：骨架 20/20、底部两端 9/9、触摸契约 9/9、头部交互 17/17、百分比口径 7/7。
测试资产同步：`.sub-head`（AI 列表）→ `.lib-head`、`.sub-tag` → `.lib-head .tag`、
AI 列表的 `scrollTop` 从 `.main` 改为 `.lib-scroll`。

## ADR-22 桌面也搬到 Wails v3：一份 `main.go`，一套绑定

**问题。** 0.3 的时候桌面是 v2、手机是 v3，两个宿主（`app/main.go` 与 `app/cmd/mobile/main.go`），
两套传输（`window.go.app.Backend.*` 与 `Call.ByName`），两条构建链（`wails build|dev` 与
`build-android.ps1`），`api.ts` 里靠运行时判定同时伺候两套。用户的话：「能否将 wails 桌面版本的
v2 迁移到 v3 中，这样就不用维护 2 个版本了」。

先量了一次成本，结论和直觉相反——业务层几乎没有活：

- v2 的 API 一共只出现在**两个 Go 文件、六处调用**里：`main.go`（窗口/绑定/文件关联/命令行）
  与 `internal/app/app.go`（原生对话框 + `EventsEmit`）。
- `internal/app.Backend` 与 `internal/webassets.Handler` 本来就是宿主无关的；同一份 `web/dist`
  已经能在两个 WebView 里跑。
- 真正的成本全在构建链：`wails.json`、NSIS 传参、`run.ps1` 的前置检查、dev 循环。

而且 v2 那条链已经**开始坏了**：v2.11 内置的 `x/tools` 读不了 Go 1.27 的导出数据
（`internal error: package "fmt" without types`），当时靠把 `GOTOOLCHAIN` 钉到 `go.mod` 的版本
糊过去；`wails.json` 的 `frontend:dev:watcher` / `serverUrl` 每改一次都要翻文档。

**决定。**

- **`app/main.go` 是唯一入口**，桌面与 Android 都是它编译出来的。平台差异只有两个
  `//go:build` 文件：`platform_android.go`（钉 `EPUBMAKER_HOME`、写 `trace.log`）与
  `platform_desktop.go`（同名空实现）。`cmd/mobile/main.go` 删掉。
- **绑定只有一个形状**：`Call.ByName('epubmaker-desktop/internal/app.Backend.<Method>')`，走宿主
  自己的 `/wails/runtime.js`，没有 npm 运行时依赖。`web/src/api.ts` 里"两套传输 + 运行时判定"
  整段删除（`hasV3Runtime` / `hasNativeDialogs` 都没了）。保留一处**注入缝**：`window.go` 存在时
  优先用它——那是给 60 个离线 Playwright 脚本伪造后端用的，不是第二套传输。
- **原生对话框改走 v3 API**：`App.SelectEpubFiles` / `SelectCoverFile` / `SelectDictFile` 用
  `application.App.Dialog.OpenFile()`，手机与桌面同一份实现（手机原先自己拼 `Dialogs.OpenFile`）。
- **拖放改成宿主事件**：`EnableFileDrop: true` + `window.OnWindowEvent(WindowFilesDropped)` →
  `window.EmitEvent('epub:dropped', paths)`，前端 `filedrop.ts` 订阅后扇出。原先靠 v2 的
  `OnFileDrop` 把路径直接塞给 `window`。
- **构建链自写，CLI 只留两件事**：`build-windows.ps1`（web bundle → 版本资源 → `go build`
  →（可选）NSIS）与 `dev-windows.ps1`（vite + 反向代理 + Go 改动自动重编重启）；`wails3` 只用来
  `generate syso` 和 `android overlay:gen`。`run.ps1` 只做转发，`Set-WailsToolchain` 整个删掉。
- **版本号单一来源**：`app/build/config.yml` 的 `info.version`，两个脚本各自
  `-X ...AppVersion=` 注入；`wails.json` 与 `cmd/mobile/build/config.yml` 都删。
- **桌面调试走 CDP**：`EPUBMAKER_DEBUG_PORT` → `Windows.AdditionalBrowserArgs` 里的
  `--remote-debugging-port`（v3 不读 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 环境变量）。

**代价与边界。**

- `wails3 build|dev|package` 用不了（go-task 在本机跑不了本仓库的脚本），所以构建链是自写的；
  但它本来就是自写的（Android 从 0.3 起就这样），只是现在两边共用同一套约定。
- **dev 没有 HMR**：反向代理拦不住 websocket 升级（asset server 对 upgrade 回 501），前端改动是
  整页刷新。`EPUBMAKER_DEV_URL` 只编译进 `!production` 构建，release 里这段代码不存在。
- **`production` tag 的语义要记住**：它关掉 WebView2 的 devtools（v3 的
  `application_production.go`），所以 `-Dev` 构建既没有 `-w -s` 也没有 `-H windowsgui`，体积
  17.3 → 25.7 MB。
- **版本资源写的是语言中立表**（`000004b0`，沿用 v2 的 `info.json` 模板）：资源本身完整，
  但本机的 PS 5.1 `.VersionInfo` 读不出字符串（`FileVersionRaw` 有值）。v2 时代一样，不是迁移引入的。
- **测试缝不许扩散**：`injected()` 只在 `api.ts` 内部用，别在组件里再判一次宿主。

**回归（都跑在真实产物上，不是编译通过就算）。** 桌面走 WebView2 CDP：
`BOOT {"href":"http://wails.localhost/","cards":69,"books":69,"dropzone":true}`、
深链接硬导航 `DEEPLINK {"llm":true}`、深链接刷新 `RELOAD {"llm":true,"books":69}`、
回书架 `SHELF {"cards":69}`。dev 循环：`viteClient:true` + `tsModules:["/src/main.tsx",…]` +
`books:69`（证明页面来自 vite、绑定仍然可用），`touch` 一个 `.go` 后日志出现
`Go changed — rebuilding` 且窗口重连后数据不变。产物：exe 17.3 MB、NSIS 安装包 9.2 MB
（版本资源 0.4.0）、arm64 APK 26.7 MB。离线回归：`shelf` 20/20、`verify` 19/19、`esc` 24/24、
`vocab-schedule` 15/15、`drop` 17/17（按新契约重写）、`mobile` 193/193；
`go build ./... && go vet ./... && go test ./...` 与 `npx tsc --noEmit` 全绿。
