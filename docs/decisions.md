# 设计取舍

记录"为什么是这样"，避免以后有人（包括我自己）把已经否决过的方案再提一遍。
每条都给出当时的证据，而不是偏好。

## ADR-1 无 HTTP、无端口

原来是 Express 后端 + `/api` 路由，迁移到 Wails 后留了一层薄 HTTP。后来全部删掉：
前端只调 `window.go.app.Backend.*`，二进制响应内联 base64。

原因：桌面单机应用里，HTTP 层只带来三个问题——端口冲突、dev 与生产两份路径、CORS/代理配置。
进程内绑定让 dev 和生产走同一条路径，打包成单 exe 也不再有资源服务器。
代价是大文件要走 base64（约 +33% 内存峰值），在单本 EPUB 的尺度上可以接受。

推论：**任何需要"再起一个服务"的功能都别想**，包括内置词库的 HTTP 查询、LLM 代理。

## ADR-2 资源主键 = 原 zip 内完整路径

落盘 `books/<id>/content/<原路径>`，导出原样还原。曾考虑扁平化（`images/0001.png`）以便管理，
但章节里的相对引用（`../images/x.png`）会全部失效，导出时还得反查映射。
保留原路径后，相对引用天然成立，导出逻辑几乎不需要资源重写。

代价：路径可能带 `..`、重名文件、大小写差异，必须在 `storage.ContentPath()` 里统一做穿越防护。

## ADR-3 分页翻页不做动画

曾做过 8 个 commit 的 3D 翻页（`.flip-turner` 双面各塞一份完整章节 HTML + `mix-blend-mode` 高光）。
在 WebView2 上严重卡顿，也没有实体书手感，已整体删除。

现在的规则：章内翻页是瞬时 `setPageIndex`（整章 HTML 常驻 DOM，翻页只是一次 `translate3d`）。
章节切换保留 130ms 淡入淡出，作用是盖住新章节 HTML 异步加载的空窗，不是装饰。

如果将来重做动画：**一次翻页只允许一个活动图层**，不要复制整章 HTML。

## ADR-4 词库不联网下载，走本地导入

实测官方 `raw.githubusercontent.com` 下载 `ecdict.csv` 约 **1.4 KB/s**（6 分 48 秒只拿到 557KB），
100MB 要十几小时。所以"首次运行自动下载词库"这个方案直接排除，不再讨论。

现状：随包分发或用户自备 csv，走 `DictImportCSV`（界面按钮 / `cmd/dictimport` 同一代码路径）。
全量 770,611 条导入耗时 8.5 秒，所以不需要进度条，按钮禁用 + 菊花即可。

词库独立放在 `dict/dict.db`（不塞进主库），是为了能整体替换、重建、删掉而不影响书库。

## ADR-5 生词本是跨书资产

`vocab.book_id/chapter_id` 只存值，**不加外键、不级联删除**。
同一个词在 A 书、B 书都会遇到；书删掉、读完了，词还得留在复习队列里。
如果挂在 `book_id` 上做级联，整理书库会顺手毁掉学习积累——这是不可接受的耦合。

## ADR-6 变形词不覆盖原型

原以为"`running` 应该还原成 `run` 再查"。完整词库证明这是错的：

- ECDICT 把每个变形都收成了独立词条，所以还原逻辑根本不触发；
- 但变形词条的释义往往只是"v. 爬（climb 的过去式和过去分词）"，只给这个等于没解释；
- 而 `running` 又有独立实义（赛跑、流动的、运转的），替换成 `run` 会丢信息。

结论：`Result.Base` 同时返回原型，界面并排显示"本体释义"+"原型及其释义"。

## ADR-7 自动入库：高频不收录 + 第二次才收录

系统没法知道哪些词"你不认识"，能捕捉的只有"你查过它"。所以自动记录 = 查完零点击入库，而非智能识别。

两个过滤条件，目的是让生词本第一页就可读：

1. **高频词永不自动收录**（`frq`/`bnc` ≤ 5000）。否则 `the`/`of`/`a` 会瞬间淹掉列表。
2. **同一个词第二次查才入库**（`vocab_seen.lookups ≥ 2`）。隐式表达"我真的不认识"，而不是"我好奇一下"。

手动"加入生词本"永远可用，不受上述限制；标过 `known` 的词不会因为再查一次被降级。

已知让步：因为词在第二次才入库，**例句只能是触发入库的那次出现**，第一次的句子没被存过。
要保住"第一次的句子"得给信号表加 4 列存首次出处，为一个例句微调不值得，已写进代码注释与测试。

## ADR-8 复习用 SM-2 排程，而不是"每天全过一遍"

上一版复习是"把没掌握的词按顺序过一遍"：没有间隔，没有下次时间，同一个词可能今天答对、
明天又出现在队首。那不是间隔重复，只是把列表换了个顺序。

现在按 SM-2（Wozniak, 1987）排程，落到五个字段：

| 字段 | 作用 |
| --- | --- |
| `interval_days` | 当前间隔（天）。0 = 从未排程（立即到期），< 1 = 十分钟重学步 |
| `ease` | SM-2 熟练度系数，起始 2.5，答对 +0.1、答错 −0.32，夹在 [1.3, 2.8] |
| `due_at` | 下次到期时间，RFC3339 UTC 秒精度；空串 = 从未排程 |
| `streak` | 连续答对次数（展示用，算法看间隔本身） |
| `lapses` | 累计答错次数 |

打分的两条路径：

- **认识**：`interval ≤ 0 → 1 天`；`< 1 → 1 天`（从重学步毕业，先挣一天）；`< 6 → 6 天`；
  其余 `round(interval × ease)`。间隔到 21 天才算 `known`——**掌握是证据，不是一次点击**。
- **不记得**：回到 10 分钟重学步，ease 下调，`lapses+1`，状态 `learning`。

为什么是 10 分钟而不是 1 天：答错时记忆最薄弱，当天再见一次才有用；推到明天等于放过。

为什么用两档而不是 SM-2 的 0–5 六档：卡片只有两个按钮。把六档硬塞进界面的结果是
用户永远只点中间那个，数据反而更差。两档 + ease 已经足够把"总也记不住的词"和
"一眼就过的词"区分开——前者间隔涨不上去，后者越排越远。

`due_at` 用定长秒精度字符串而不是 SQLite 的 `datetime()`：一是 **字符串比较即时间顺序**
（RFC3339Nano 不满足，`…:00.5Z` 会排在 `…:00Z` 前面），二是 Go 侧算好再比较，
不依赖 SQLite 对纳秒小数的解析行为。

队列因此只剩一句判断：`status <> 'ignored' AND (due_at = '' OR due_at <= now)`。
`known` 不再等于"永不出现"——间隔到期的老词会回来，这才是长间隔复习的意义。
手动点"已掌握"不记为复习，但会把下次检查排到三周后（`ignored` 才是真正的退出）。

已验证：1 → 6 → 16 → 45 天的阶梯、答错回到 10 分钟步、ease 触底 1.3、
到期的 `known` 词会重回队列、老库迁移后旧词一律"立即到期"（各有测试）。

## ADR-9 拖放导入走 Wails 原生桥，而不是 HTML5 拖放

书架一直写着"拖入 epub"，但实现是 `onDrop` 里 `preventDefault()` 之后调用
`SelectEpubFiles` —— 也就是拖完弹一个文件选择框，等于没导入。原因不是懒：webview 的
drop 事件里只有 `File` 对象，**没有文件系统路径**，而这个应用的导入是"从磁盘读"，
从来没有上传通道（见红线 2）。所以在纯前端里那份拖进来的数据是读不出来的。

现在的路径：`main.go` 打开 `DragAndDrop.EnableFileDrop`，Wails 把 drop 坐标与
WebView2 的 additional objects 交给 Go 侧解析成绝对路径，再以 `wails:file-drop`
事件回传前端；`web/src/filedrop.ts` 订阅一次，把路径交给书架页已有的
`ImportPaths`。前后两个入口（按钮、拖放）在 `Library.importPaths()` 汇合。

三个必须同时成立的点，缺一个就退化：

1. `EnableFileDrop` 为真 —— 否则 Go 侧直接丢弃 `file:drop` 消息；
2. 前端订阅了 `OnFileDrop` —— Wails 的 window 级 `dragover/drop` 监听是**随订阅安装**的，
   没订阅时连 `preventDefault` 都没有，拖进来的文件会把 webview 导航过去（页面变成一本
   epub 的二进制），这是本 bug 之外更严重的默认行为；
3. `useDropTarget: false` —— 默认值要求落点元素带 `--wails-drop-target` CSS 属性，
   而书架希望"拖到哪都能放"，所以关掉它，由页面自己判断该不该导入。

订阅放在 `App` 而不是书架页：它同时是"拦住默认导航"的那一层，晚一步注册就有一个
drop 仍然会毁掉页面。

拖到书架以外的页面不导入，只提示回书架 —— 导入要落到书架的列表状态上，别的页面没有
可更新的东西，静默失败比一句提示更糟。

降级：浏览器里没有 `window.runtime`（`run.ps1 web` / 纯前端调试），`canResolveDropPaths()`
为假，drop 退回打开文件选择框 —— 那条路仍然有路径，仍然能导入。

## ADR-10 0.4 AI 能力：BYOK + 底部面板 + 全链路 grounding

原型：`docs/prototypes/0.4-ai-mobile.html`（2026-10-25 与用户逐屏定稿）。

范围（按优先级）：

| 能力 | 触发 | 喂给模型的本地数据 | 优先级 |
| --- | --- | --- | --- |
| 上下文释义 | 词卡「✦ AI」 | 原句（`LookupWord` 第 7 参早已传入并落库）；**义项不发了，见文末修正 1** | P0 |
| 整句翻译 + 长难句拆解 | 划词工具栏「✦ AI」 | 选区句子（`sentenceAt` 已取到） | P1 |
| 章节导读 | 顶部工具条「✦ AI 导读」 | 章节正文（截断 6000 字，发送前明示） | P1 |
| 人物卡片 | 读完一章 | 各章导读结果合并去重 | P2（可选） |

**原句填空出题押后（v0.5 候选）**：初版设计是 mask 生词本已存的 context 句让用户填。
否决理由（用户提出）：例句本就印在复习卡上，遮一个字再填回去只是重复回忆同一句话，
边际价值接近零，还会诱导「照着句子找词」而非回忆词义。重启方向：先跨章检索该词在本书
其他位置的真实出现（零生成、真实语料），不够再让 AI 按书中风格造新例句。

### 为什么是 BYOK，不做内置代理

内置代理 = 给「无服务端」应用加服务端（ADR-1 的推论明确点名了 LLM 代理），
还引出计费与密钥中转的隐私问题。所以：设置页填 base URL + key + model
（预设 DeepSeek / 通义 / Kimi 等 OpenAI 兼容端点），密钥存本机 0600 文件。
**没有 key 时全部功能照常**，AI 入口显示「未配置」并引导去设置——AI 是可选层，
不是门槛。

### 入口形态：底部面板（方案 C），不是词卡内嵌（方案 A）

| 维度 | A 词卡内嵌（未选） | C 底部面板（选定） |
| --- | --- | --- |
| 操作步数 | 1 次点击 | 2 次（点按钮 + 看面板，可滑动关闭） |
| 词卡负担 | 结果让词卡变长 | 保持轻量，和现在一样高 |
| 长内容适配 | 义项高亮、结构化拆解排不开 | 面板 76% 高，结构化展示 |
| 手势风险 | 无新增 | 模态需排除 swipe 翻页（红线 5f，抽屉已有先例） |
| 实现成本 | 只改 dict-card | 新增面板组件（三个 surface 复用） |

「一步看完」让位于「长内容展得开」：拆解输出是结构化的，卡内一行行排会挤；
且面板组件三个 surface 都要用，单点成本摊薄。

### 翻译与拆句合并为一个视图

不拆 tab：手机上 tab 是隐藏内容，用户永远只看到第一个；译文 + 拆解一次请求、
一个滚动视图看完，信息密度更高。缓存键 = 精确提示词的 hash（实现期修正：
原设计是「句子文本」，改为 system+user 整段 hash——提示词改进会自动失效旧缓存，
用户为更好的答案再付一次费，是正确的行为）。

### 隐私确认：每次问

导读是唯一发送整章正文的功能，不提供「记住选择」——每次发送前都明示
（字数 + 服务商），这是红线 2a「显式动作」在正文尺度上的执行方式。
其余能力只发单词/句子，不需要额外确认。

**实现期修正（0.4 收尾）：确认框先做配置预检。** 没有配置时弹「还没有配置」
+ 去设置，而不是让用户点完「生成导读」再收到一个错误——一个只能以失败告终的
确认框不算确认。同时 `NotConfigured` 的错误文案带上 `ai.json` 的实际路径：
「我明明配了」几乎总是另一个 `AppHome` 下的第二份配置，路径一眼就能定位到问题。

### 导读入口：顶部菜单，不是章首浮标

设计期放在章首浮标（`position: fixed`，只在第 1 页/滚动到顶时可见），理由是
不能往正文流注入（红线 6）。实机使用后 john 判定入口位置错了：浮标压在第一行
文字上方，读起来像正文的一部分，而且只在章首存在——想再看一次得先翻回章首。

改为顶部工具条里的一个按钮（手机是返回/标题/✦AI/书签那一排，桌面是与
目录、书签、滚动同排的 `✦ AI 导读`）。章首浮标与它的滚动跟踪一起删除，
正文上方不再有任何浮层。代价是手机上要先点一下上下边距打开工具条，
收益是它和「目录/书签」同类归位，任何一页都能用。

### 红线对照

- 2a 显式触发：全部能力都是点击触发，无任何打开页面即请求；
- 2 无 HTTP：前端只调 `Backend.AI*` 绑定，二进制内联 base64 的老规矩不变；
- 2b 超时：单次 15s 上限，失败 UI 给重试、**不写墓碑**——与 `FillVocabGlosses`
  的区别：那是不存在的词（写墓碑避免重问），这是网络故障（下次还该能重来）；
- 2c 落缓存：新表 `ai_cache`，key = 精确提示词 hash；**只有非空回答落缓存**
  （实现期修正：空回答也不写墓碑——空回答是软失败，「重试」按钮必须永远真实，
  空回答走缓存会让用户以为已经问过了）。网络/HTTP 故障同样不写。
  二次查看零延迟、离线可回看。

### 实现顺序

`internal/ai`（OpenAI 兼容客户端 + ai_cache 存取）→ Backend 绑定 → 设置页 →
阅读器三处入口。先写测试（httptest 假服务商）：缓存命中、墓碑/重试语义、
超时、错误映射、上下文裁剪。

### 验收后的四处修正（2026-10-26，真机 + 用户反馈）

**1. 上下文释义不再喂义项，改成「直接解释 + 整句翻译」。**
原设计（本 ADR 首版）是让模型在 ECDICT 的编号义项里挑选，理由听起来更「grounding」。
实机第一次用就露馅：ECDICT 把一个词的全部义项塞在一行里
（`n. 1.儿童，小孩 2.婴儿，胎儿 3.子女，孩子 …`），模型拿到这种「大杂烩义项」挑不出来，
输出「这些义项都不贴合本句」——而义项里明明就有贴合的。既然模型自己会翻译，
直接让它「结合句子解释这个词 + 翻译整句」既短又更贴语境，`senses` 参数整个删掉
（前后端签名同改）。副产品：词卡上的 ✦ AI 不再依赖词典查到义项，查不到也能问。

**2. 空回答必须说清是哪种空。**
用户报的「AI 没有返回内容」在旧代码里是所有失败共用的兜底文案，而真实原因往往是
`finish_reason=length`（拆句的 JSON 很长，1024 max_tokens 不够；推理型模型的
思考也会先吃掉预算）或模型只填了 `reasoning_content`。现在 `ai.Reply` 带回
`finish_reason / usage / reasoning_content`，错误分成四句：
被截断、只输出思考过程、`content_filter` 等其他 finish、真的空回答。
`DefaultMaxTokens` 提到 4096（上限而非目标，不多花钱）。
另：截断的 JSON（`{` 开头但没有右括号）不再当散文硬展示，按「截断」报错。

**3. 本机诊断日志（`internal/logx`）。**
AI 出错依赖一个开发者摸不到的服务商，没有记录的话 bug report 只能是一句
「它没反应」。所以：内存环形缓冲 300 条 + `logs/app.log`（512 KB 轮转，保留一代），
记录每次 AI 请求（system/user 全文、模型、baseUrl）、回答（finish、耗时、token、
正文）、空回答的原因、缓存命中、设置保存、前端 JS 错误与每次路由跳转。默认开启
（出事时关着的日志等于没有），可在「设置 → 诊断日志」关闭/清空/查看/复制，只在本机，
不上传。开关存 `logs/logging.json`，不写进 `config.json`（那份是要跟着备份走的）。
跨端：桌面 v2 绑定与手机 v3 `Call.ByName` 都自动带上新方法。

**4. 返回手势的哨兵改成「全栈一个」+ 延迟到提交后丢弃。**
黑屏的根因不在阅读器，在 `backNav`：原实现每个浮层压一条历史哨兵，卸载时靠
`history.state` 判断「刚才那下 pop 是不是我自己的」。词卡 → AI 面板这种嵌套栈里，
两个浮层会互相丢掉对方的哨兵；下一次返回于是 pop 掉一个真实页面条目，守卫为了
关浮层把这次 pop 吞掉，URL 和画面从此错位——再划几下就得到「白/黑屏 + 再按退出」。
现在：**打开多少浮层都只压一条哨兵**，栈空时才丢；丢弃延到 effect flush 结束后的
微任务（这样「关词卡 + 开面板」同一提交里不会误丢），且只在
